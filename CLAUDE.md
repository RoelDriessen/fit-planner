# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A personal fitness/exercise planner ("Fit Planner") synced across devices via Supabase (Postgres + Auth + Realtime + Edge Functions). Vanilla HTML/CSS/JS frontend, no build step, no npm dependencies — `@supabase/supabase-js` is loaded via CDN `<script>` tag (UMD build) as `window.supabase`. Sibling project to the "Gerechten" recipe app one directory up (`../`) — same architecture and conventions, entirely separate Supabase project and data.

Plans movement/sport/exercise (including back/hip/knee rehab-style exercises) into a real weekly schedule, tracks completion with a simple points & levels system, and sends real push notifications (daily "what's planned today" + weekly "go plan your week") — including on iPhone when added to the Home Screen.

**Routines, not loose exercises, are what gets scheduled and scored.** Exercises are individual moves in a shared, household-wide library (rug/heup/knie/sport/etc., editable only by whoever created each one). A routine ("training") bundles a set of exercises together — each exercise gets its own rep count, the routine as a whole gets a set count and a point value — and it's routines that get planned into the week and marked done. Routines are private per profile; exercises are shared. See "Multi-user model" below for what "profile" means here.

## Setup (one-time, per Supabase project)

1. Create a **new, separate** free project at supabase.com (do not reuse the Gerechten project — this app needs its own tables/auth account).
2. Run `supabase-schema.sql` in the project's SQL Editor — creates `app_users`, `exercise_categories`, `exercises`, `routines`, `routine_exercises`, `sessions`, `user_settings`, `push_subscriptions`, `exercise_attachments`, the private `exercise-attachments` Storage bucket + policy, RLS policies (every row scoped to `auth.uid()`), and Realtime on every table. Leave the `pg_cron`/`pg_net` block at the bottom commented out for now — it needs the Edge Function deployed first (step 6). The whole file is idempotent (`if not exists`/`drop policy if exists`/`on conflict do nothing`), so if you already ran an earlier version, just re-run the whole file to pick up new tables/columns. **Exception**: a project that ran a version of this file from before routines/multi-user existed should run `supabase-schema-2-routines-multiuser.sql` instead — it's a guarded migration for an already-provisioned project, and it destructively truncates `sessions`/`push_subscriptions`/`user_settings` (their shape changes in ways that can't carry old rows forward), so only run it if that data is disposable.
3. In Project Settings -> API, copy the Project URL and anon public key into `js/config.js` (copy `js/config.js.example` first). RLS is what actually protects data, so the anon key is safe to ship client-side.
4. In Authentication -> Sign In / Providers -> Email: enable the Email provider, and turn **"Confirm email" off** — this is a single-user access-code login (see below), not a real multi-user signup flow.
5. Generate a Web Push VAPID keypair: `npx web-push generate-vapid-keys`. Put the public key in `js/config.js` as `VAPID_PUBLIC_KEY`. Keep the private key for step 6.
6. Deploy the reminders Edge Function and set its secrets:
   ```
   supabase functions deploy send-reminders --no-verify-jwt
   supabase secrets set VAPID_PUBLIC_KEY=... VAPID_PRIVATE_KEY=... VAPID_SUBJECT=mailto:you@example.com CRON_SECRET=<any-random-string>
   ```
7. Uncomment the `pg_cron`/`pg_net` block at the bottom of `supabase-schema.sql`, fill in your project ref and the same `CRON_SECRET`, and run just that block in the SQL Editor. This schedules the Edge Function to run every 10 minutes and check whether it's time to send anyone a reminder.

### Multi-user model: one shared household login + client-side profiles

This is the single most important thing to understand about this codebase's security model before touching auth, `app_users`, or any RLS policy.

**The household login is the only real security boundary.** Identical trick to the Gerechten app: the UI's `#authScreen` only ever asks for a code, no email field. Under the hood it's Supabase email+password auth against one fixed, internal account: `window.APP_ACCOUNT_EMAIL` (in `js/config.js`) is used as the email for every `signInWithPassword`/`signUp` call, and the code the user types is the password. First use: "Code instellen" calls `signUp` once; after that, "Inloggen" is used every time, on every device. **This part is deliberately unchanged and must stay that way** — the client never auto-authenticates with a hardcoded shared password, because that password would have to live in `js/config.js`, which is committed to this project's *public* GitHub repo (see the repo's own README/deploy setup); embedding it there would let anyone extract full read/write DB access from the public source.

**Multiple people ("profiles") share that one login.** After the household login succeeds, `#profileScreen` shows a picker: tiles for each `app_users` row, tap one and enter that profile's own short code to switch into it (hashed client-side, see below — never sent or compared server-side), or "+ Nieuw profiel" to create one. The active profile is remembered on-device for 2 hours (`saveProfileSession()`/`loadStoredProfileId()`, `localStorage` key `fitPlanner.activeProfile`, sliding — each successful silent restore pushes the expiry forward another 2 hours), not indefinitely and not never: a real PIN-free window rather than either extreme, since iOS can reload a standalone PWA's page (and therefore all in-memory JS state) more often than a person would consider "a new session" just from backgrounding it. Once that window lapses, the picker + PIN is required again. That household code screen itself is normally only ever seen once per device/browser regardless: Supabase's JS client persists the session (its own `localStorage` entry + automatic token refresh) across app opens on its own, so `#authScreen` only reappears if that session is missing or has been revoked, not on every visit. "Wissel gebruiker" in Instellingen clears the stored profile session and returns to the picker without a full Supabase sign-out — the household session stays intact, only the active profile is cleared.

**RLS cannot and does not distinguish between profiles.** Every table's RLS policy is still the same flat `for all using (auth.uid() = user_id) with check (auth.uid() = user_id)` shape used everywhere in this codebase — and since every profile shares the *same* `auth.uid()` (the one household account), that policy only proves "someone who knows the household password", never "this specific profile". All actual separation between profiles — which routines/sessions/settings/push subscriptions belong to whom, and who may edit a given shared exercise — is enforced **only in the client** (`js/app.js`), by filtering on `app_user_id` (or `created_by_app_user_id` for exercises). A determined caller with the anon key could read or write any profile's data directly via the REST API; this is an accepted tradeoff for a personal/household tool, not an oversight — but it means never leaning on RLS to hide one profile's data from another when adding new tables or endpoints, and never treating this the way you'd treat real multi-tenant auth.

**`app_users.code_hash`** is `SHA-256(code + ":" + id)` computed client-side (`sha256Hex()`, Web Crypto's `crypto.subtle.digest`), where `id` is generated client-side (`crypto.randomUUID()`) *before* insert specifically so it can double as a per-row salt — since RLS can't hide this table from other profiles either (see above), an unsalted hash would be a free rainbow-table target for anyone in the household. This is hardening, not a real security guarantee: a profile code is a convenience/identity PIN, not a password.

**Exercises are shared, routines are private.** `exercises`/`exercise_categories` have no `app_user_id` at all — every profile sees and can use the same library. `exercises.created_by_app_user_id` records who made each one; `isExerciseEditable()` in `app.js` is the (client-side only) gate that hides edit/delete/upload controls for exercises you didn't create. `routines`/`routine_exercises`/`sessions`/`user_settings`/`push_subscriptions` all carry a real `app_user_id` column and are loaded with `.eq("app_user_id", currentAppUserId)` — scoped by construction, not by remembering to filter in every render function.

**Known, accepted limitation**: a Web Push subscription is one-per-browser-per-origin, not one-per-profile. If two people ever share the same literal device/browser for this PWA, only whichever profile most recently clicked "Meldingen inschakelen" on that device will receive pushes there — not something this app tries to solve.

## Commands

No build/lint/test tooling. To develop, serve the directory locally:

```
python3 -m http.server 8000
```

Then open `http://localhost:8000`. `localhost` is exempt from the service-worker secure-context requirement, so this is fine for everything except testing real Web Push on an iPhone — see below.

### Testing Web Push on an actual iPhone

Service workers (and therefore Web Push) require a real secure context off of `localhost`. To test on-device: deploy to any static HTTPS host (GitHub Pages, Netlify, Cloudflare Pages) or run a tunnel (`ngrok http 8000` / Cloudflare Tunnel) during development. Then, on the iPhone: open that HTTPS URL in Safari, "Share" -> "Add to Home Screen", and launch it from the Home Screen icon (Web Push does not work in a plain Safari tab, only in an installed standalone PWA, and only on iOS 16.4+).

## Architecture

- `supabase-schema.sql` — source of truth for the DB schema, RLS policies, and realtime publication (idempotent, safe to re-run). The `pg_cron`/`pg_net` block at the end is commented out by default; it's the first thing in this codebase family (vs. the Gerechten app) that schedules server-side work, and needs the Edge Function deployed and its `CRON_SECRET` known before it can be uncommented and run.
- `js/config.js` (copy from `js/config.js.example`) — Supabase URL/anon key, the access-code account email, and the public VAPID key, filled in per-deployment.
- `index.html` — three top-level screens toggled via `hidden`: `#authScreen` (household login) -> `#profileScreen` (profile picker/creation) -> `#app`. Inside `#app`, `.layout` holds `.sidebar` (labelled Dashboard / Deze week / Routines / Oefeningen / Instellingen — the internal `data-view` value for the first item is still `"today"`, matching `#todayView`/`renderToday()`/etc. in `app.js`; only the user-facing label changed) and `.main`, which toggles between `#todayView`, `#weekView`, `#routinesView`, `#exercisesView`, `#settingsView`. `#exerciseModalOverlay` edits a shared exercise's details; `#routineModalOverlay` edits a private routine's details plus its list of exercises-with-reps.
- `css/style.css` — same design tokens and breakpoints as the Gerechten app (`--bg`/`--surface`/`--accent`/etc. custom properties, dark-mode-first with a `prefers-color-scheme: light` override, sidebar horizontal-chip-row below 720px vs. a real column above it, `env(safe-area-inset-*)` for the iPhone notch/home-indicator).
- `js/app.js` — all logic in one flat file, no framework/build step:
  - `sb` is the Supabase client; all reads/writes go through it. Shared/household state (`exerciseCategories`, `exercises`, `appUsers`) and per-profile state (`routines`, `routineExercises`, `sessions`, `userSettings`, `pushSubscriptions`, `exerciseAttachments`) are both loaded in full into `let` globals — fine at personal scale, not designed to paginate. The per-profile loaders (`loadSessions`/`loadRoutines`/`loadUserSettings`/`loadPushSubscriptions`) filter with `.eq("app_user_id", currentAppUserId)` at the query itself, so downstream rendering code never has to remember to re-filter — see "Multi-user model" above for why that matters here specifically.
  - Screen flow is a 3-state machine, not the old 2-state auth/app toggle: `sb.auth.onAuthStateChange` -> `showApp()` (household login OK — including a silent restore of a persisted Supabase session, most of the time — loads shared data, then either silently restores a still-valid remembered profile or calls `showProfilePicker()`) -> picking/creating a profile calls `enterApp()` (loads per-profile data, starts realtime, renders). `showAuth()` and `switchProfileBtn`'s handler both tear back down to an earlier stage.
  - `setupRealtime()`: one Realtime channel listening for `postgres_changes` on every table (shared and per-profile alike), filtered to the household's `auth.uid()` — the same value for every profile, so this fires for everyone's changes and each handler just refetches through the per-profile-filtered loaders above to get back to a correctly-scoped state. The `app_users` handler additionally self-heals: if the active profile was deleted from another device, it bounces back to the profile picker.
  - **Sessions are date-based, not template-based**: each `sessions` row has a real `scheduled_date`, so history, the points/level total, and the daily streak all fall directly out of querying that one table — there's no separate stats table.
  - **Points & levels**: completing a session (`setSessionStatus(id, "done")`) snapshots `points_awarded` from the *routine's* current `points_value` (so editing a routine's point value later doesn't retroactively rewrite history) and sets `completed_at`. `totalPoints()`/`computeLevel()`/`computeLevelProgress()`/`computeStreak()` derive everything else client-side from the loaded `sessions` array (already scoped to the active profile) — see the "points / level / streak" section of `app.js`.
  - **Week planning**: `renderWeek()` builds 7 day cards from `weekDates()` (Monday-start, `weekOffset` weeks from the current week), scheduling **routines** (not individual exercises) via each day card's quick-add form (delegated `submit` listener on `#weekDays`). "Kopieer vorige week" (`copyPreviousWeek()`) duplicates last week's sessions onto the corresponding dates of the viewed week — the main lever for fast, low-friction planning.
  - **Exercise categories** (`exercise_categories`) are shared household-wide, same as exercises — rug/heup/knie/sport/etc. are user-created rows with a `PALETTE`-assigned color, not a hardcoded enum. The chip filter row in "Oefeningen" (`renderExerciseCategoryFilters`) is single-select (click again to clear).
  - **Exercise modal** (`openExerciseModal`/`renderExerciseModal`): opened by clicking an exercise row; name/category/duration/notes/video URL save individually on blur/change, no separate "Save" button. `isExerciseEditable(ex)` gates everything else: for an exercise you didn't create (`created_by_app_user_id` doesn't match the active profile), every field is rendered `disabled`, the archive/delete buttons and the photo-upload control are hidden, and a "door {naam}" badge (`#exerciseModalOwnerBadge`) explains why — client-side UI gating only, see "Multi-user model" above. Archiving is a soft toggle (`archived` boolean, exercise stays visible in the list, dimmed); delete is real and immediate (no confirmation dialog) and also removes that exercise's Storage files first.
  - **Exercise video** (`exercises.video_url`): `parseVideoEmbed()`/`videoEmbedHtml()` best-effort embed a YouTube/Vimeo link (via `-nocookie`/`player.vimeo.com` iframes) or a direct video file link (native `<video>`); anything else falls back to a plain "open in new tab" link, since arbitrary sites usually block iframe embedding.
  - **Exercise photos** (`exercise_attachments` + the private `exercise-attachments` Storage bucket): PNG/JPG only, 10MB max (validated client-side against `ALLOWED_MIME`/`ALLOWED_EXT`/`MAX_FILE_BYTES` — the PNG/JPG restriction itself is only enforced client-side). Files live at `<user_id>/<exercise_id>/<random>-<filename>`; previews use short-lived `createSignedUrl()` URLs, cached client-side for ~50 minutes via a shared `signedUrlCache` `Map` (`getSignedUrl()` — used by the modal's attachment grid, the exercise-list thumbnail below, and the workout player, so the same photo isn't re-signed on every re-render). Clicking a photo opens `#lightboxOverlay` (`openLightbox`/`closeLightbox`).
  - **Exercise list thumbnails** (`renderExercises()`/`loadExerciseThumbnails()`): `firstImageAttachmentFor(exerciseId)` picks the oldest attachment for that exercise (attachments load ordered oldest-first, so this is simply the first photo ever attached, mirroring the Gerechten app's cover-image convention) and shows it as a 44×44 `.exercise-thumb` in the list row — hidden entirely for exercises with no photo, no placeholder box.
  - **Routines** (`routines` + join table `routine_exercises`): `openRoutineModal`/`renderRoutineModal` mirror the exercise modal's save-on-blur/change pattern for name/sets/points/notes. The "Oefeningen in deze routine" list (`routineExerciseList`) lets you add an exercise from the shared library with its own `reps`, remove one, edit `reps` inline, or reorder via simple up/down buttons (`moveRoutineExercise()`, which just swaps the `position` column between two adjacent rows — no drag library). Deleting a routine cascades its `routine_exercises` at the DB level and sets any referencing `sessions.routine_id` to null (history/points already awarded are preserved, same rationale as the old exercise-delete behavior).
  - **Workout player / "Starten"** (`#workoutOverlay`, wired from a `.start-btn` on each *session* row — both `#todaySessionList` and the week view's day cards, only shown while `status === 'planned'` — calling `startSessionWorkout(sessionId)`): deliberately not reachable from the Routines view/modal at all — starting is an action on something you've actually planned, not on the routine definition, so there's no "find or create today's session" guesswork like an earlier version of this had. `buildWorkoutSequence()` flattens a routine's ordered exercises into one linear list repeated once per `routine.sets` (e.g. sets=3 with exercises `[A,B]` becomes `[A,B,A,B,A,B]`), so stepping forward/back through sets-of-exercises is just walking one flat array (`workoutStepIndex`) rather than tracking nested round/exercise counters. "Klaar, volgende" (or "Klaar — voltooien" on the last step) advances via `workoutNext()`; reaching the end calls `setSessionStatus(id, "done")` on the underlying session (awards points exactly like checking it off anywhere else). The × close button exits at any point without touching the session's status — only actually finishing the sequence marks it done. Individual steps aren't persisted anywhere; only completing the whole sequence writes anything.
    - **Video/photo toggle**: if an exercise has both `video_url` and an attached photo, `#workoutMediaToggle` shows a two-way pill switch (🎥 Video / 🖼 Foto) above the media; with only one of the two, the toggle stays hidden and that one just shows (`.workout-media:empty` collapses the block entirely if neither exists — no empty gap). Which one is selected first is driven by `user_settings.preferred_workout_media` (Instellingen → "Workout-weergave", saved immediately on change, no separate Opslaan button) falling back to whichever of the two is actually available for that specific exercise if the preferred one is missing.
    - **Landscape-phone-specific layout, not a forced/locked orientation**: the Screen Orientation Lock API isn't supported in iOS Safari (this app's primary target) even in standalone PWA mode, so there's no reliable way to force rotation — instead `@media (orientation: landscape) and (max-height: 520px)` switches `.workout-panel` to a two-column layout (media left, exercise info right, full-width header/action bar) instead of the portrait vertical stack, deliberately targeted at a phone propped up sideways mid-workout (not tablets/desktop landscape, which don't hit the height constraint). A small `#workoutRotateHint` ("Kantel je toestel voor een breder beeld") nudges this in portrait, hidden automatically in the landscape layout and whenever the current step has no media to view.
  - **Profile picker** (`#profileScreen`, `showProfilePicker()`/`renderProfileTiles()`): tiles for each `app_users` row; tapping one reveals an inline code-confirm form (`sha256Hex()`-hashed and compared client-side against `code_hash`), "+ Nieuw profiel" creates one (name + code + confirm, salted hash generated with a client-side `crypto.randomUUID()` used as both the new row's `id` and the hash salt). Zero profiles yet (first-ever use) skips straight to the creation form. `showApp()` only calls this when there's no still-valid remembered profile (see "Multi-user model" above for the 2-hour sliding window) — a successful code-confirm or new-profile creation both call `saveProfileSession()` to (re)start that window. The code inputs (`#profileCodeInput`, `#newProfileCode`/`#newProfileCodeConfirm`) use `type="password" inputmode="numeric" pattern="[0-9]*"` — masked entry with a numeric keypad on mobile, without actually restricting `code_hash` to digits-only (a physical keyboard or autofill can still supply letters; this is a UI nudge toward the common case, not a validation rule).
  - **Test reminders** (`sendTestReminder(type)`): calls the `send-reminders` Edge Function with `{mode: "test", type, app_user_id: currentAppUserId}` via `sb.functions.invoke` (which auto-attaches the session's JWT) — see the Edge Function bullet below for what that triggers server-side.
  - **Push notifications**: `enablePushNotifications()` (user-gesture-triggered, from Instellingen) and `trySilentPushResubscribe()` (best-effort, runs on every login if permission was already granted — self-heals a rotated/expired subscription) both register `service-worker.js`, call `pushManager.subscribe()` with `VAPID_PUBLIC_KEY`, and upsert the result into `push_subscriptions` (keyed by `endpoint`, tagged with the active profile's `app_user_id`). On iOS, the "Meldingen inschakelen" button is hidden (with an install hint shown instead) unless the app is already running standalone from the Home Screen — `Notification.requestPermission()` only works from that context on iOS, and only from a direct user-gesture handler.
- `service-worker.js` — push-only service worker (no offline caching): shows the incoming notification, and on click focuses an already-open tab or opens a new one.
- `supabase/functions/send-reminders/` — Deno Edge Function with two invocation modes, both handled by the same `Deno.serve` entry point in `index.ts`:
  1. **Cron mode** (empty/no `mode` in the request body): invoked on a schedule by `pg_cron`/`pg_net` (not by a logged-in user, hence `--no-verify-jwt` + a shared `x-cron-secret` header check). For every `user_settings` row (one per profile) it computes that profile's local date/time from their stored IANA timezone (`timeWindow.ts`, DST-safe via `Intl.DateTimeFormat`, not string round-tripping), and — guarded by `last_daily_reminder_sent_date`/`last_weekly_reminder_sent_date` so a 10-minute bucket match can't double-send — sends a Web Push message via `npm:web-push` (`sendPush.ts`; Deno's npm-compat, chosen over hand-rolling the RFC 8291/8292 encryption+VAPID signing). Every lookup in this path (`push_subscriptions`, `sessions`) is scoped by `app_user_id`, not `user_id` — every profile shares the same `user_id`, so a `user_id`-scoped query here would silently mix every profile's data into every other profile's push. Expired subscriptions (`404`/`410` from the push service) are deleted automatically.
     - **Timing precision**: `pg_cron` ticks on fixed 10-minute clock boundaries (`*/10 * * * *`), not relative to any user's configured time. A reminder set for e.g. 14:16 will actually arrive on the next tick that falls inside `isWithinBucket()`'s `[14:16, 14:26)` window — in practice that's the 14:20 tick, so up to ~10 minutes of "slop" after the configured time is expected behavior, not a bug.
     - **Daily message content** (`buildDailyReminderBody()`, shared by both modes): lists the actual routine names (+ time, if set) for that date's `status = 'planned'` sessions, e.g. `"Vandaag: Ochtendroutine rug (08:00), Avondwandeling (19:00)"` — not just a count. Sessions already marked `done`/`skipped` are deliberately excluded (the reminder is about what's still open, not a full day recap); falls back to a "niets gepland" message when there's nothing left planned.
     - **Delivery failures are logged, not silently swallowed**: `sendPush()` (`sendPush.ts`) `console.error`s the target push service's host + status + error message on any non-2xx/thrown failure (visible via `supabase functions logs send-reminders` or the dashboard's Logs Explorer), and `sendToAll()` returns `{sent, failed}` counts that both invocation paths fold into their response/`results` — a partial or total delivery failure is now visible instead of the caller only ever seeing `"sent": "daily"` regardless of whether anything actually reached the device.
  2. **Test mode** (`{mode: "test", type, app_user_id}` in the body): triggered on-demand by the two test buttons in Instellingen. Authenticated by validating the caller's normal Supabase session JWT (`admin.auth.getUser(token)`) rather than the cron secret — since `app_users` isn't tied to Supabase Auth, this only proves "someone who knows the household password", not "this is really that profile" (consistent with this app's whole multi-user model, see above). Sends immediately to the named profile's subscriptions, skips the time-bucket check, and — critically — never touches `last_daily_reminder_sent_date`/`last_weekly_reminder_sent_date`, so a test send can never suppress or delay the real scheduled one. Message title is prefixed `(TEST)`.
- `manifest.json` + `icons/` — enables "Add to Home Screen" for a standalone (fullscreen, no browser chrome) iPhone experience. Icons were generated from `icons/icon.svg` via macOS's built-in `qlmanage`/`sips` (no external tooling) — regenerate with a different `icon.svg` and re-run the same rasterize/resize commands if you want a different look.
